## 4. Browser journeys and expected results

### A. Common UI, localization and authentication (014, 031–040, 051–060)

- [ ] **A01 — Shared appearance:** At `/`, `/register`, `/login`, seller and admin pages, logo/globe render correctly; black/white/orange styling and readable contrast are consistent. No broken image, missing font or horizontal overflow.
- [ ] **A02 — Navigation:** Visible links lead to the right screen; current navigation reflects role and login state; browser refresh and Back do not unexpectedly erase valid state.
- [ ] **A03 — Register:** Valid customer details create an account; show a useful confirmation/verification state; a second submission does not create a duplicate.
- [ ] **A04 — Registration errors:** Required fields, malformed email, weak password and mismatched confirmation show understandable inline errors; duplicate email does not reveal sensitive account details.
- [ ] **A05 — Verify email:** Open the actual link from test email; verification succeeds once, updates the account, and reused/invalid/expired links receive a clear safe result. Resend respects its documented controls.
- [ ] **A06 — Login:** Verified valid credentials work; wrong credentials fail without exposing which secret was wrong; unavailable/unverified/suspended account behavior follows the documented policy.
- [ ] **A07 — Session:** Refresh page and open a second tab; login remains valid as designed. Logout removes access; Back or direct protected URL cannot restore privileged data. Test revoke-current and revoke-other session actions if surfaced.
- [ ] **A08 — Password recovery:** Request a reset; open the received link; set a new valid password; old password fails and the new one succeeds. An invalid/used/expired reset link must not change the account.
- [ ] **A09 — English/Bangla:** Change language on registration, seller and admin pages; labels, validation, empty states and messages follow the selection; refresh preserves or intentionally resets the choice according to the documented rule.
- [ ] **A10 — Bangladesh formatting:** Display BDT correctly; currency text is never shown as points. Phone/address fields accept documented Bangladesh formats; timestamps displayed to users align with Asia/Dhaka settings.
- [ ] **A11 — Phone/provider gating:** If OTP provider is configured, test send/verify/resend, wrong/expired code and rate limits. If Google/Apple support is only architectural at 039, record **not enabled**; do not assume fully working social-login buttons are required yet.

### B. Roles, tenancy and audit (041–050)

- [ ] **B01 — Direct URL guards:** While logged out, open `/admin`, `/admin/users`, `/admin/roles`, `/admin/sellers`, `/seller`, `/seller/kyc`, `/seller/products` and `/seller/products/new`; protected content is blocked or redirects safely.
- [ ] **B02 — Role guards:** Customer cannot use seller/admin screens; Seller A cannot use admin controls; ordinary Admin cannot use Super Admin-only actions. Navigation hiding alone is insufficient: direct URL and API requests must be denied.
- [ ] **B03 — Seller isolation:** Seller A cannot read/edit Seller B's application, staff, settings, media or products by replacing an ID or slug in a URL or API request. Seller B's data must never appear in Seller A's lists.
- [ ] **B04 — Staff scope:** Seller A staff can perform only assigned actions; revocation takes effect without exposing Seller A owner-only or Seller B data.
- [ ] **B05 — Sensitive actions:** Approval, rejection, suspension, role changes and product publication record the actor/time/reason where required. Audit views do not display passwords, access tokens or raw secrets.
- [ ] **B06 — Session/CSRF checks:** Forms and mutations reject unauthenticated or cross-origin requests per documented browser security policy; errors do not expose stack traces or database details.

### C. Seller lifecycle (061–070)

- [ ] **C01 — Apply:** Submit seller application; required fields and duplicates are validated; the applicant sees a clear pending status after refresh.
- [ ] **C02 — KYC:** Upload a valid document; preview or file reference is visible only to authorized people. Invalid type, size or missing required information produces a clear error without saving a fake success state.
- [ ] **C03 — Review:** Admin sees pending applications, reviews the correct applicant's data/documents and can approve or reject with documented reasons. Applicant sees the new status after refresh.
- [ ] **C04 — Resubmit:** Rejected applicant can correct and resubmit; previous decisions remain in history where required. Another seller cannot view the case.
- [ ] **C05 — Store identity:** Approved seller edits store name, branding, public identity and allowed contact details; changes persist; protected or disallowed details do not leak publicly.
- [ ] **C06 — Settings:** Payout/banking profile, tax, shipping, order and notification defaults validate required fields; sensitive banking data is masked in ordinary views. Do not claim a real payout has occurred.
- [ ] **C07 — Suspension:** Admin suspends Seller A; seller sees an appropriate status and restricted actions are actually blocked. Reactivation restores permitted access without losing records.
- [ ] **C08 — Staff:** Owner invites staff, grants a limited scope and revokes it; staff sees only the intended store and actions. Activity/audit records identify who made changes.

### D. Catalog foundations (071–080)

- [ ] **D01 — Categories:** Admin creates parent and child categories; hierarchy, sorting/status and selection in a product form are correct. Invalid cycles or unsupported deletes are rejected safely.
- [ ] **D02 — Brands:** Create or request a brand, apply its approval flow and confirm an unapproved brand cannot silently become public.
- [ ] **D03 — Collections:** Create a curated collection and, where supported, a rule-based collection; eligible product membership updates according to the documented rule.
- [ ] **D04 — Attributes:** Create option sets such as Color/Size; valid variants can be generated; duplicate or invalid option combinations are rejected.
- [ ] **D05 — Locale/SEO:** Category and brand labels have the required English/Bangla handling; slugs, metadata and visibility are correct for their current stage.
- [ ] **D06 — Guidance:** Seller catalog templates/help explain category, price, points, image and approval requirements accurately.
- [ ] **D07 — Bulk import/export:** Valid input imports intended records; a malformed row produces a row-specific error without leaking another seller's data. Export contains only the authorized seller's records.
- [ ] **D08 — Moderation:** Duplicate/suspicious submissions appear in the proper review workflow; approve/reject results and reasons persist. Seller cannot approve own protected content unless policy explicitly permits it.
- [ ] **D09 — Cross-surface sync:** A category or brand created/approved by Admin becomes available in the appropriate seller form; disable/archive changes propagate after refresh.

### E. Product management and publication (081–090)

- [ ] **E01 — Draft:** Seller A creates a draft at `/seller/products/new`, returns to `/seller/products`, refreshes and edits it. Draft data persists; Seller B cannot see or alter it.
- [ ] **E02 — Price versus points:** Enter **BDT 10,000** and **1,000 Product Points**. The UI clearly labels two independent fields; missing/invalid price or Product Point blocks publication. Do not treat points as BDT or silently convert one field into the other.
- [ ] **E03 — Variants:** Add multiple Color/Size combinations. Every intended combination appears once; changing options updates the grid safely; removing a variant gives a clear warning if relevant.
- [ ] **E04 — SKU/barcode:** Valid identifiers save; duplicate SKU and invalid barcode cases follow the documented uniqueness policy with an actionable error. Rejected submissions do not overwrite a different product.
- [ ] **E05 — Media:** Upload a valid image and, if configured, video; preview/order/cover image persist. Invalid type or size fails. A deleted image disappears only from the intended product; inaccessible media does not expose another seller's file.
- [ ] **E06 — Descriptions:** Save title, description, specifications and rich content in supported locales; reload and check rendering, escaping, missing-translation fallback and formatting.
- [ ] **E07 — Logistics/tax:** Weight, dimensions, shipping attributes and any configured tax fields validate input and persist. Do not invent a tax percentage not supplied by approved configuration.
- [ ] **E08 — Submission:** Incomplete draft cannot publish. Valid draft moves through submit/review/approve/publish statuses, with actor, status and allowed next action visible on seller and admin sides.
- [ ] **E09 — Rejection/edit:** Admin rejects with reason; seller sees it, edits and resubmits. Seller cannot bypass approval by changing a URL or request payload.
- [ ] **E10 — Public visibility:** If public listing/detail is integrated, only published products appear at `/products` and `/products/<actual-slug>`; draft/rejected/archived products are not public. Full polished storefront is due later at 115–120.
- [ ] **E11 — Archive/slug:** Archive a product and verify its public state changes correctly. If a published slug changes, old links follow the documented redirect/history policy rather than accidentally exposing the wrong item.
- [ ] **E12 — History:** Version/audit view shows old/new values, actor and time for product changes without rewriting prior versions. Verify a previous change can be identified after refresh.
- [ ] **E13 — Filters/empty states:** Seller and Admin lists show correct status, search, pagination or filters that have been implemented; empty, loading and error states are clear; Seller B's records do not appear in Seller A's counts.

## 6. Checks a browser view cannot establish by itself

Request the milestone completion reports and run the project's available quality commands. Do not infer these properties from screenshots.

- [ ] **Source mapping:** Each finished milestone 001–090 has its required completion report: changed files/migrations, decisions and sources, added behavior, test results, security/localization/financial checks, outstanding configuration and next milestone.
- [ ] **Quality gate:** `bun run lint`, `bun run typecheck`, `bun run test`, `bun run openapi` and `bun run build:local` pass when those commands are available in the current project. Record any documented exception instead of treating a skipped command as a pass.
- [ ] **Database:** Product, category, seller, role and KYC migrations apply on an isolated test database; seeds are repeatable. Changes made in the browser survive restart; history is preserved.
- [ ] **API contract:** `/api/v1/openapi.json` documents implemented auth/seller/catalog/product operations. Validate success and error status, machine-readable error codes, ownership and missing-auth cases against current OpenAPI.
- [ ] **Money/points:** Price persists safely in BDT/poisha units; Product Point persists as its own unit. No reward, wallet credit, leaderboard result or commission is claimed merely from the product-entry screen at 090.
- [ ] **Security:** Seller B object IDs fail for Seller A at the API, not only in the UI. Admin/Super Admin restrictions also hold at the API. Upload access is scoped; audit records omit secrets.
- [ ] **External dependencies:** Email, OTP, media storage, social auth, and payout behavior are separately marked configured, mocked, blocked or deliberately deferred. An unconfigured provider is never shown as a completed successful integration.

## 7. Recommended end-to-end demonstration for milestone 090

1. Register Customer C, verify email and sign in.
2. Apply as Seller A, submit KYC; Admin reviews and approves; Seller A signs in and completes store settings.
3. Admin creates/approves a category and brand. Seller A creates a product with BDT 10,000 price, 1,000 Product Points, variants, unique SKU, image and English/Bangla text.
4. Seller A submits it; Admin approves; Seller A sees the new status. If a public listing is implemented, Customer C can view **only the published product**.
5. Seller B logs in and cannot see/edit Seller A's product or KYC. A direct URL/API request for Seller A's object is denied.
6. Admin rejects a second product with a reason; Seller A edits and resubmits. Product history and decision/audit trail show the changes.
7. Repeat key screens at mobile width and in Bangla; refresh after mutations to verify persisted state.
